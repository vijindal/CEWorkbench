# N-Phase Equilibrium Solver (Hillert's Method) — Implementation Plan

## Context

CEWorkbench currently solves single-phase CVM equilibria only (`CVMGibbsModel.getEquilibriumState`, via `CalculationService.calculate`/`calculateScan`). The user has a working Mathematica reference implementation (`phaseq`) of Hillert's method for **multi-phase** equilibrium — given an overall composition and a set of candidate phases (each possibly a different structure/model), it solves for which phases are stable, their amounts, their individual compositions, and equal chemical potentials across phases. This capability does not exist in the Java codebase at all (confirmed via search — no "Hillert", "multi-phase", or partial stub anywhere in `src/`).

This is a substantial new capability, not an extension of the existing single-phase solver: it needs a chemical-potential derivative that doesn't exist yet anywhere in the model layer, a new outer/inner nested iteration, and a new public API entry point, because `calculate()`/`calculateScan()` are structurally single-`ModelSession`-shaped.

**Directive: build the groundwork first.** Before writing `HillertSolver.java` itself, get the existing single-phase code ready to support it — the widened gradient/Hessian and the reusable validity check (`isValidParams`) are prerequisites, not part of the solver class itself. Steps 1-2 below (in "Build order") come first, as their own reviewable unit of work.

**Standing directive: every derivative used anywhere in this solver — `Gu`/`Guu`, `G0m`'s `T`-derivative, and everything `PerPhaseStep`/`HillertSolver` compute — must be analytical, never finite-differenced, in production code.** Finite-differencing is permitted only as a one-off, throwaway validation check (e.g. a `runScratch` sanity check comparing an analytic result against a numeric approximation) to confirm an analytic implementation is correct — it must never become, or be left as, the actual code path the solver executes. See the "Widened gradient/Hessian" and `G0m` sections below for what's already analytical and verified this way.

Investigated and confirmed prior to this plan:
- `ModelSession` is immutable and safe to instantiate once per phase.
- `CVMGibbsModel` is stateful/non-thread-safe — needs one instance per phase, never shared.
- `ThermodynamicWorkflow` has a single-slot cache — use one instance per phase (no source change needed).
- `Gu`/`Guu`/`Hu`/`Su`/`Suu` are all **∂/∂u** (internal CVCF correlation functions only, length `ncf`), never ∂/∂x (composition). No chemical potential exists anywhere in the codebase yet.
- `CMatrixPipeline.evaluateCVs`/`buildFullCVCFVector` show `cv = C·[u; x]` is **exactly linear** in both `u` and `x` — `x` enters the same linear map `u` does, just via trailing columns. Verified: `cmat` column width is `ncf+K` (mole fractions only) even for ordered structures with an extra order parameter (`eta`), consistent with `buildFullCVCFVector`'s own contract and the fact that B2 single-phase solving already works today — so the analytic derivative approach below is sound, not resting on an unverified assumption.
- The existing single-phase solver has a known, unresolved near-edge (dilute-composition) convergence stall (documented in CLAUDE.md). The outer Hillert loop re-invokes single-phase equilibration every outer iteration per phase, so this fragility can propagate into the outer loop, not just show up at the initial guess.
- **Revised after reading a second Mathematica reference function, `delxGCVM`** (the actual per-phase driver `phaseq` calls, distinct from the earlier single-phase `CVMBINCE.minimize`): its `Gx`/`Gxx`/`GxT`/`GxP` are **not** a separate composition-only derivative bolted onto the existing `u`-only gradient/Hessian. They are the gradient/Hessian of `G` with respect to the **full internal-parameter vector `y`** (called `ipl` there, length `nip = ncf + K`), i.e. `u` and composition **together as one vector** — exactly matching `CVMGibbsModel.buildFullCVCFVector`'s existing `uFull` layout. This changes the shape of the work below: **widen the existing `calGu()`/`calGuu()` to length `nip`** (covering both the `u` block and the trailing `x` block in one gradient/Hessian), rather than adding a separate side-by-side `calGx()`/`calGxx()` pair. `Gu`/`Guu` in the widened sense subsume what this plan originally called `Gx`/`Gxx`.
- `delxGCVM` also reveals two things not previously modeled:
  1. **`GxT`/`GxP` — temperature/pressure derivatives of the gradient.** Used to extrapolate the per-phase linear system across a `ΔT`/`ΔP` step (the reference solver supports T/P scanning during equilibration, not just fixed-T). `GxT` is derivable from the existing linear-in-T ECI structure (`CECEvaluator`'s `eci = a + b*T`) but is not computed anywhere currently — genuinely new. `GxP` has no pressure dependence in this codebase at all (no `P` term anywhere in `CECEvaluator`/`CVMGibbsModel`) — **out of scope for v1**, treat as always zero unless/until pressure dependence is added elsewhere first.
  2. **The per-phase Newton step already includes a Lagrange multiplier (`λ`) enforcing `Σ Δy_composition = 0`** — i.e. composition changes are constrained to stay on the simplex (mole fractions still sum to 1) as part of the *same* linear solve that produces `Δu` and `Δx` together, not as a separate renormalization pass afterward.
- **`G = G0m + Gm` — a pure-element reference energy (`G0m`) is missing entirely, confirmed necessary, and now has a concrete source.** `calGcecvm` shows CVM's `G` is the sum of `G0m` (pure-element reference) and `Gm` (the CVM mixing energy — what `CVMGibbsModel.calculateG()` currently computes; confirmed by grep, no `GHSER`/reference-energy term exists anywhere in this codebase today). `G0m` doesn't depend on `u` at all, so it contributes zero to `Gu`/`Guu`'s `u`-block, but is generally nonzero in the composition block — and it's **not optional** for Hillert's method specifically: single-phase validation to date only ever checked one phase's mixing energy at one composition (self-consistent without an absolute reference), but comparing/equalizing chemical potentials **across different phases/structures** is only physically meaningful if every phase's `G` shares the same zero. See the dedicated section below — the user has shared the full source and it's ready to port.

## Widened gradient/Hessian, not a separate chemical-potential method

`delxGCVM` computes one gradient `Gx` (length `nip`) and one Hessian `Gxx` (`nip`×`nip`) per phase, in the **joint** `(u, x)` parameter space — this is what feeds the per-phase Newton step described below, not a standalone "chemical potential" quantity computed independently of `Guu`.

Revised implementation: widen `calculateGu()`/`calculateGuu()` (and the underlying `calculateSu()`/`calculateSuu()`, `src/main/java/org/ce/model/cvm/CVMGibbsModel.java`, ~lines 615-681) to loop over `l = 0 .. ncf+K-1` instead of `l = 0 .. ncf-1` — the C-matrix column range already exists (`cm[incv].length == ncf+K`, verified), this is a loop-bound change plus updating the few call sites that currently assume length `ncf`, not new derivative math. `H` is linear in `u` only (`Hx = 0`, confirmed both from this codebase's `calculateH` — a pure `Σ eci[l]*u[l]` sum with no `x` term — and from `delxGCVM`'s structure), so the widened `Hu` simply has zeros in the trailing `x` block; no change to `calculateHu`/`calculateHuu` needed beyond returning the right length.

Chemical potential itself, if/when needed as a standalone reported quantity (e.g. for GUI display), is then just `μ_i = widened-Gu[ncf+i]` at the converged point — a slice of the widened gradient, not a separate calculation.

Verify with a one-time finite-difference sanity check (`runScratch`) of the widened gradient's trailing block against numeric `∂G/∂x` at a converged single-phase point — not a permanent code path, just a validation step before trusting it in the outer loop.

`GxT` (new): derive analytically from `CECEvaluator`'s linear-in-T ECI structure — `∂eci/∂T` is just the `b` coefficient of each `a + b*T` term, so `∂Gu/∂T = Σ (∂eci/∂T)[l] * (∂cv-linear-coefficient structure)`, computable by the same C-matrix walk. Build only when the T-scanning capability is actually needed — not required for a fixed-T two-phase v1.

## `G0m`: pure-element reference energy (lattice stability)

Source confirmed from the user's Mathematica `calG0m`/`calG0`/`calGHSERxx` functions: standard SGTE/Dinsdale-style unary lattice-stability polynomials, one piecewise function per (element, structure), form `a + b·T + c·T·ln(T) + d·T² + e·T³ + f/T [+ higher-order terms]`, valid over specific `T` ranges (e.g. `GHSERMO` has one form below 2896 K, another above). `calG0(element, phase, T)` dispatches to the right one per element; some structures are their own base reference (`GHSERxx`), others are offsets from another structure (`GFCCMO = 15200 + 0.63*T + GHSERMO`, `GLIQMO = 41831.347 - 14.694912*T + 424.519e-24*T^7 + GHSERMO` below 2896 K, etc.). `calG0m(elements, phase, T) = Σ x_i · calG0(element_i, phase, T)` — simple composition-weighted sum, no mixing physics (all mixing is in `Gm`).

Elements covered in the reference: **Mo, Nb, Re, Ta, Ti, V, W, Zr**, each with `GHSERxx` plus `BCC_A2`/`FCC_A1`/`HCP_A3`/`LIQUID` variants (not every structure exists for every element, e.g. V has no FCC_A1 in the reference — mirror that exactly, do not invent missing data). This is already the full element set CEWorkbench's existing Hamiltonians use (Nb-Ti-V, Nb-Ti-V-Zr, Mo-Nb-Ta), so no new elements need sourcing.

**Implementation**: new class `model/equilibrium/LatticeStability.java` (co-located with the rest of the Hillert-solver-only code, since `G0m` is not needed by the existing single-phase path at all). Mechanical, literal translation of the Mathematica source — one Java method per `GHSERxx`/`GLIQxx`/`GFCCxx`/`GHCPxx`/`GBCCxx` function, same piecewise `if (T < threshold)` structure, same coefficients, plus a `g0m(List<String> elements, String phase, double[] composition, double T)` composition-weighted sum matching `calG0m`. This is finite porting work, not open design — verify with a handful of spot-checks (pick a few `(element, phase, T)` triples, hand-evaluate the Mathematica formula, compare to the Java output) rather than a broader design review.

`G0m`'s own `T`-derivative (feeding `GT`) is straightforward: every `GHSERxx` term is an explicit closed-form function of `T` (polynomial + `T·ln(T)` + reciprocal/higher powers), so `∂G0m/∂T` differentiates term-by-term with no numerical differentiation needed — same mechanical-porting character as `G0m` itself.

`G0m` is purely additive to `G`/`H` (not `S` — it is not an entropy term) and only touches the composition-block entries of the widened gradient described above; it does not change how the `Gu`/`Guu` widening itself is implemented.

## New package: `model/equilibrium/`

Sibling to `model/cvm/`, `model/mcs/`, `model/hamiltonian/` — a distinct algorithm from single-phase CVM minimization even though it calls `CVMGibbsModel` as a subroutine per phase.

- **`PhaseState.java`** — per-phase mutable holder: `ModelSession session`, `CVMGibbsModel model` (own instance, never shared), `double amount`, `double[] composition`, `double[] u`, last `ModelResult` (whose `Gu`/`Guu` are now the widened joint-space versions per above — no separate `Gx`/`Gxx`/`Gux` fields needed), `boolean isStable()` (`amount > tolerance`, mirrors the reference's amount-sign-only stability handling — not a rigorous Gibbs phase rule check; document this explicitly as inherited, not an oversight).

- **`PerPhaseStep` — implemented as a method on `CVMGibbsModel` itself, not a separate class** (revised decision — see note below). The per-phase local Newton solve, ported from `delxGCVM`: given a phase's current `(u, x)`, its widened `Gu`/`Guu` (now covering the joint `nip = ncf+K` space per the section above), and a **trial chemical-potential vector `μ`** supplied by the outer loop, assembles and solves one linear system for `(Δy, λ)`, where `Δy` is the joint `(Δu, Δx)` step and `λ` is the Lagrange multiplier enforcing `Σ Δx_i = 0` (composition change stays on the simplex). This *is* the "equilibrium matrix" this plan originally described as a separate `EquilibriumMatrix` class assembling mass-balance and potential-equality rows directly — `delxGCVM` shows that assembly happens **per phase**, parameterized by whatever `μ` the outer loop is currently trying, not as one global matrix across all phases at once. Reuses the existing private `LinearAlgebra.solve` call pattern already used by `minimize()`. Returns `record PerPhaseStepResult(double[] deltaY, double[] deltaComposition, double lambda)` (mirrors `delxGCVM`'s `{delnN, delyN}` return, plus the Lagrange multiplier for callers that want it).
  - **Placement decision (revised from the original plan)**: `PerPhaseStep`'s only real inputs beyond `(uFull, μ)` are `CVMGibbsModel`'s own widened `Gu`/`Guu` and `isValidParams` — a separate class would mostly be a thin wrapper reaching into already-public/private `CVMGibbsModel` state. CLAUDE.md already documents `CVMGibbsModel` as deliberately both an evaluator and an optimizer (`minimize()` lives there too), so a second, differently-parameterized Newton solve over the same physical state is consistent with that precedent rather than a new pattern. Implemented as `public PerPhaseStepResult solvePerPhaseStep(double[] uFull, double[] mu)` directly on `CVMGibbsModel`, next to `minimize()`, clearly documented as Hillert-solver-specific (not part of the single-phase `getEquilibriumState` path) so the two Newton solvers don't get confused with each other despite sharing a class.
  - The **outer-loop** mass-balance/potential-equality assembly across phases (mirroring `phaseq`'s own `genEqMat`/`fracRules`) is a genuinely separate concern — not solved per-phase, only per-outer-iteration across all stable phases at once — and still needs its own class, tentatively `EquilibriumMatrix.java` in `model/equilibrium/`, scoped to just that outer-loop coupling.

- **`HillertSolver.java`** — outer/inner nested iteration:
  - `EquilibriumResult solve(List<PhaseState> phases, double[] overallComposition, double T, int jtrMax, double tol, Consumer<String> progressSink, Consumer<ProgressEvent> eventSink)`
  - Outer loop (`jtr`, up to `jtrMax`): for each phase, equilibrate/evaluate via a call structured like `delxGCVM` (not directly `CVMGibbsModel.getEquilibriumState`, which solves a phase at *fixed* composition — here composition is part of what's being solved for), producing `G`, widened `Gu`/`Guu`, and (via `PerPhaseStep`) `Δy`/`Δcomposition` for the current trial `μ`. Assemble/solve the outer mass-balance + potential-equality system (`EquilibriumMatrix`, scoped per the revision note above) to get updated `μ` and phase amounts.
  - Inner backtracking loop (`itr`, cap 10): full step on `(amount, uFull)` jointly per phase using the `Δy` from `PerPhaseStep`; validate via a new `CVMGibbsModel.isValidParams(uFull)` — **extract** the existing private cluster-variable-bounds check currently buried in `minimize()` (`minClusterVariable()`) into a reusable public method rather than duplicating the `[0,1]` logic; halve step and retry on invalidity, matching the reference's plain backtracking (not the analytic-boundary-ratio `stpmx`/`calculateStepLimit` approach, which was found to stall near dilute compositions).
  - **Every outer iteration, check each phase's `converged`/validity status explicitly.** Never let a non-converged or invalid inner phase feed silently-wrong `G`/`Gu` into the outer equilibrium assembly — report per-phase non-convergence (`PhaseResultEntry.phaseConverged`) or abort the whole solve with a clear message. Build this in from the start; do not add it as an afterthought.
  - Convergence: norm of the `Δy` update below `tol` for **all** phases simultaneously (mirrors `phaseq`'s `Min[normList]<=10^-10` check).
  - Exclude `amount ≤ 0` phases from that iteration's constraint assembly.
  - **`updateComp` — confirmed from the Mathematica reference.** For a CVM-modelled disordered phase (`BCC_A2`/`FCC_A1`/`HCP_A3`, the only case this plan targets), Mathematica's `updateComp` is `compList = Take[yN, -numComp]` — i.e. composition is literally the **trailing K entries of the internal parameter vector** (`u2ListN[[ip]]`, our `uFull`). This matches `CVMGibbsModel.buildFullCVCFVector`'s own layout exactly (`uFull = [u (non-point CFs) ; x (mole fractions)]`): the composition is *already* the trailing slice of `uFull`, not something requiring a separate inversion step. So after the joint Newton step updates a phase's `uFull`, the new composition is read off directly — `PhaseState.composition = uFull[ncf .. ncf+K-1]` — no new code needed beyond bookkeeping in `HillertSolver`/`PhaseState`. (Mathematica's `updateComp` also has a `LAVES_C15`/`CEF` sublattice branch — irrelevant here, out of scope, not a CVM phase.)

- **`PhaseEquilibriumResult.java`** — immutable output DTO (mirrors `ThermodynamicResult`): `List<PhaseResultEntry>` (`phaseLabel, amount, composition, G, H, S, phaseConverged`), plus `overallConverged`, `outerIterations`, `finalResidualNorm`.

## Public API entry point

Add to `CalculationService` (`src/main/java/org/ce/calculation/workflow/CalculationService.java`) — not a separate service class, to keep "one entry point per calculation kind, all callers bottom out here":

```java
public PhaseEquilibriumResult calculateEquilibrium(
        List<PhaseSpec> phaseSpecs,          // each: ModelSession + double[] initialGuessComposition
        double[] overallComposition,
        double temperature,
        double tolerance,
        Consumer<String> textSink,
        Consumer<ProgressEvent> eventSink) throws Exception
```

- `PhaseSpec` — `record PhaseSpec(ModelSession session, double[] initialComposition)`, alongside `Conditions`/`ConditionsScan` in `org.ce.calculation`.
- Internally: one `PhaseState` (own `CVMGibbsModel`) per `PhaseSpec`, delegate to `HillertSolver.solve(...)`, wrap as `PhaseEquilibriumResult`.
- Each phase's own single-phase equilibration still goes through `CVMGibbsModel.getEquilibriumState` exactly as `ThermodynamicWorkflow.runCvm` does today — no change to that path.
- GUI wiring (a new `Mode` in `CalculationDescriptor`, a new panel) is **out of scope for v1** — CLI/programmatic verification only.
- New CLI subcommand in `ui/cli/Main.java`, e.g. `./gradlew run --args="phaseq <elements> <phase1>:<x1guess> <phase2>:<x2guess> <overallX> T <T>"`, following the existing `calc_min`/`type2` argument-parsing style (read `Main.java`'s existing subcommand dispatch before implementing, to match conventions).

## Build order (groundwork first, two phases before N)

Build `EquilibriumMatrix`/`HillertSolver` **N-phase-shaped from the start** (`List<PhaseState>`), but verify with N=2 first — the Mathematica reference's only concrete worked example is a two-phase (C15/BCC) case, enough to exercise every mechanism (mass balance, chemical-potential equality, joint inner Newton step, phase-stability exclusion) without simultaneously debugging N-way indexing.

**Phase A — groundwork on existing code — DONE:**

1. ✅ **Widened `calGuFull()`/`calGuuFull()` to joint `(u, x)` space.** Implemented as *new, separate* public methods (`calGuFull`, `calGuuFull`, backed by private `calculateGuFull`/`calculateGuuFull`/`calculateSuFull`/`calculateSuuFull`) rather than widening `calGu`/`calGuu`/`calculateGu`/`calculateGuu` in place — those remain byte-for-byte untouched because `minimize()`'s Newton-Raphson loop solves against them directly (`LinearAlgebra.solve(Guu, negGu)` sized exactly `ncf`); widening in place would have silently changed what the single-phase solver solves each iteration, not just what it reports. Verified: leading `ncf` entries of `calGuFull()` match `calGu()` exactly; trailing (composition-block) entries pass a finite-difference check (0.2%→0.02% relative error as step size shrinks 10x, correct first-order convergence). All three CLAUDE.md regression values unaffected.
2. ✅ **Extracted `isValidParams(double[] u, double[] moleFractions)`** — public, stateless (no `setU`/`setX`, doesn't touch `currentCv`), side-effect-free (verified: probing it doesn't perturb a model's cached converged state). **Correction during implementation**: initially ported with the same `tcdis-1` (point-type-excluding) scope as `minClusterVariable`/`findMin`, by analogy — but the user shared `calGmcecvm`'s actual construction of `cvt` (`Table[..., {i,1,tcdis}]`, the *full* range, no exclusion), confirming `isValidParams` is a genuinely broader check than `minClusterVariable`: it also validates the composition/point block, catching a trial composition that's drifted to a pure-element corner (`x_i=0` or `1`), which the narrower version would miss. Corrected to loop `t < tcdis` (full range). Re-verified all cases including the corner-composition case.
3. ✅ **`LatticeStability` (`G0m`)** — `src/main/java/org/ce/model/equilibrium/LatticeStability.java`. Literal port of `calG0`/`calGHSERxx`/`calG0m` for Mo, Nb, Re, Ta, Ti, V, W, Zr. Two structures (`GBCCTI`, `GHSERV`/`GHCPV`/`GLIQV` above 4000K) had no defined branch in the source — mirrored as an explicit thrown exception rather than guessing an extrapolation. Verified with 8 spot-checks against hand-evaluated formulas (both temperature branches, a structure-offset formula, a 3-way piecewise case, composition-weighted sums, and the undefined-pair exception) — all exact matches.

**Directive: every derivative used anywhere in this solver must be analytical, never finite-differenced, as production code.** This applies to `Gu`/`Guu`/`GuFull`/`GuuFull` (already true — closed-form C-matrix sums), `G0m`'s `T`-derivative (`GT`'s pure-element contribution — see gap below), and every derivative `PerPhaseStep`/`HillertSolver` computes going forward, including any future `GxT`/`GxP`. The one place finite-differencing appears anywhere in this plan is the *validation* step for the widened gradient (a one-time `runScratch` sanity check comparing the analytic result against a numeric approximation) — that is a correctness check on analytic code, not a code path the solver itself ever executes, and must stay that way.

**Gap identified while enforcing this directive**: `∂G0m/∂T` (needed for `GT`, i.e. `∂G/∂T` at fixed `uFull` — used by `delxGCVM`'s `GT`/`GxT` and ultimately by entropy, since `S = -∂G/∂T`) was described in the `G0m` section above as "straightforward, term-by-term, no numerical differentiation needed" but was never actually implemented in `LatticeStability.java`. Add analytic `T`-derivatives of every `GHSERxx`/`GLIQxx`/etc. polynomial (mechanical term-by-term differentiation of each piecewise branch — `d/dT[a + b*T + c*T*ln(T) + d*T^2 + ...] = b + c*(ln(T)+1) + 2*d*T + ...`) as a **Phase A follow-up step**, before `PerPhaseStep` needs `GT`, so there is never a point where the only available `GT` is a placeholder or a finite-difference stand-in.

**Phase A is now fully complete, including step 3b. Next: Phase B, step 4 (`PerPhaseStep`).**

3b. ✅ **Added analytic `∂G0m/∂T` to `LatticeStability`.** One `dXxxDt` method per `Xxx` (`ghserMo`→`dGhserMoDt`, etc. — 8 elements × up to 4 structures each), each mirroring its counterpart's exact piecewise branch structure via term-by-term differentiation (`d/dT[a+bT+cT·ln(T)+dT²+eT³+f/T+...] = b+c(ln(T)+1)+2dT+3eT²-f/T²+...`), plus `dG0Dt` (dispatch, mirrors `g0`) and `dG0mDt` (composition-weighted sum, mirrors `g0m`). Verified with 19 finite-difference spot-checks spanning every element, every piecewise branch (including the two "undefined above 4000K" cases), structure-offset formulas, and the composition-weighted sum — all matched to `1e-8`–`1e-10` relative error (the expected precision for a correct analytic derivative validated by `O(h²)` centered finite-difference at `h=1e-4`). No finite-differencing anywhere in the production code — the check was validation-only, per the "everything analytical" directive.

**Directive going forward, restated for Phase B**: `PerPhaseStep`'s `(Δy, λ)` linear system must be assembled from `delxGCVM`'s actual analytic derivative expressions (widened `Gu`/`Guu` + `G0m`'s `T`-derivative where needed) — never a numerically-differentiated Jacobian as a shortcut, even for a first working version.

**Phase B — new solver, two-phase first:**

4. ✅ **`CVMGibbsModel.solvePerPhaseStep`** — implemented as `public PerPhaseStepResult solvePerPhaseStep(double[] uFull, double temperature, double[] mu)` on `CVMGibbsModel` (see placement decision above), assembling and solving the `(ncf+K+1)×(ncf+K+1)` linear system directly from `calculateGuFull`/`calculateGuuFull` (fully analytic, no finite-differencing). Verified with 3 structural checks at Nb-Ti, T=1000, x=(0.5,0.5): (1) `mu` set to exactly match the current gradient's composition block gives `deltaY≈0`, `λ≈0` — correctly finds "no move needed" when already at the target stationary point; (2) symmetric `mu=(m,m)` at the symmetric composition gives a symmetric near-zero `deltaComposition`; (3) an asymmetric `mu` gives an asymmetric composition step, with the Lagrange constraint `sum(deltaComposition)=0` holding to floating-point precision (`~1e-17`) in both cases. All three CLAUDE.md single-phase regression values unaffected.
   - **Numeric cross-check against the Mathematica reference — done, with a known/pre-existing caveat, not a new bug.** The user shared `delxGCVM`'s actual symbolic output (`GN`, `delnN`, `delyN`, `eListN`, `SN`, `HN`, `GxxN`) for Nb-Ti-V BCC_A2 at T=1000, x=(0.33,0.33,0.34), y=random-mixing — reproducible exactly (same `getPhaseData` call shape the user uses). Comparing our widened Hessian's diagonal against the reference's `GxxN` diagonal at the identical state: **18 of 21 entries match to ~1e-6 relative error** (rounding-precision agreement). The 3 mismatches are fully explained, not mysterious: (a) `v3ABC1`/`v3ABC3` are swapped between our `CvCfBasis` order and the reference's `u2List` order — this is the *exact same* known, already-documented CLAUDE.md issue the user explicitly said to leave unfixed earlier this session (confirmed by cross-referencing the swapped values); (b) the entire `v21` (1st-NN pair) and `v22` (2nd-NN pair) blocks are swapped between the two orderings — a second, previously-undiscovered ordering difference, same *kind* of issue as (a), not a new physics bug (both blocks' values match the reference exactly, just at each other's positions). Confirmed both are ordering/labeling differences, not computational errors, by verifying every mismatched value reappears exactly at the position the swap predicts.
   - **User's explicit decision: leave both ordering differences unfixed**, consistent with the earlier `v3ABC1`/`v3ABC3` precedent — `solvePerPhaseStep` is internally self-consistent (own CF order used consistently throughout, Lagrange constraint holds, diagonal values physically correct) even though its index labels don't share a common convention with the Mathematica reference's `u2List`.
